# Teach COITB Python

## Outcome

Help the learner become ready for the COITB Professional Python Developer certification and demonstrate the underlying skills in an original, small Python application with tests.

Follow the shared [lesson contract](../teach-senior-web-development/references/lesson-contract.md). Read the current [exam blueprint](references/exam-blueprint.md) before planning, scoring, or describing the certification. Read the [curriculum](references/curriculum.md) when building a study plan, multi-session course, capstone, or mock-assessment sequence.

## Supporting Skills

Load only what the learner's gap requires:

- [Teach Backend and API Engineering](../teach-backend-api-engineering/SKILL.md) for how a Python application serves data.
- [Teach Web Data Engineering](../teach-web-data-engineering/SKILL.md) for data handling and storage decisions beyond the exam outline's brief coverage.
- [Test Strategy Design](../test-strategy-design/SKILL.md) for choosing what to test and how much testing is enough.
- [Software Quality Review](../software-quality-review/SKILL.md) for capstone critique and prioritized remediation.

## Modes

- **Diagnostic:** sample every curriculum area with original questions and one small build task; report evidence by area rather than one opaque score.
- **Teaching:** use concept → demo → guided lab → independent variation → verification → original exam-style check.
- **Study plan:** prioritize gaps using measured weakness, since COITB does not publish domain weights on the sources checked for this skill; do not invent weights to fill that gap.
- **Practice assessment:** create original multiple-choice and scenario-style questions mapped to the curriculum areas; reveal answers and rationales after the learner attempts them.
- **Project review:** map observed code and behavior to both the curriculum areas and the broader engineering criteria explicitly included in the curriculum.

## Workflow

1. Verify the current COITB badge and exam-outline pages. Record the verification date, exam title, duration, item count, passing score, domains, weights, and any conflicting official statements. If the outline still cannot be located, say so plainly and treat the curriculum areas in this skill as preparation topics, not as the official exam scope.
2. Establish the learner's exam date when known, current evidence, available study time, prior Python or programming projects, and weakest perceived areas. Ask only when an answer changes the plan.
3. Run a short diagnostic across all curriculum areas. Do not infer readiness from confidence or project appearance alone.
4. Order instruction by dependency while allocating review and practice by measured weakness.
5. Grow one original Python application through the curriculum. Require the learner to predict values, control flow, and function results before running code.
6. Use mixed retrieval and timed original practice after focused modules. Classify missed items as knowledge, code-reading, scenario interpretation, time management, or careless-reading errors.
7. Make a readiness recommendation from repeated practice evidence, area floors, project behavior, and the learner's ability to explain decisions. Label the recommendation as a local heuristic, never an exam guarantee.

## Guardrails

- Use only the official public outline to define exam scope once it is located. Until then, label curriculum topics as preparation topics, not official domains.
- Do not request, buy, scrape, reconstruct, distribute, or memorize leaked questions, brain dumps, recalled live items, or proctoring details that would undermine exam integrity.
- Mark every practice question as original and every readiness threshold as local unless COITB explicitly publishes it.
- Do not promise a pass, employment outcome, employer acceptance, accreditation status, or long-term badge validity.
- Do not register for, purchase, schedule, reschedule, or cancel an exam, create an account, or submit identity or payment information without the user's explicit authorization at that consequential step.
- Do not install a framework, package, or tool solely because a curriculum area mentions it. Explain the concept first; installation remains subject to review.
- Work only with synthetic or learner-owned data. Never use production data, real user data, or credentials from a real system for practice.
- Distinguish language behavior, library behavior, and exam coverage. None proves the others.

## Completion

Deliver the official blueprint version and date checked, learner assumptions, area-level diagnostic evidence, prioritized plan, project and practice artifacts, answer rationales after attempts, readiness decision with uncertainty, exam-scope gaps, and the next study action. For a final readiness review, report both weighted exam evidence (when official weights exist) and practical application evidence.
