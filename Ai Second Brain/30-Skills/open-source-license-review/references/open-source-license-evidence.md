# Open Source License Evidence

Verified: 2026-10-21

## Primary Standards and Maintainer Sources

- [Open Source Initiative approved licenses](https://opensource.org/licenses) is the canonical OSI list and explains that approval follows OSI's license-review process.
- [Open Source Definition](https://opensource.org/osd) defines the distribution conditions required for software to be described as open source; visible source code alone is insufficient.
- [SPDX License List](https://spdx.org/licenses/) provides standardized identifiers, license and exception texts, canonical URLs, matching guidance, deprecation information, and an OSI-approved indicator. Listing does not itself mean OSI approval or legal compatibility.
- [REUSE Specification 3.3](https://reuse.software/spec/) defines a human- and machine-readable approach for associating copyright and SPDX license expressions with covered files and maintaining the corresponding license texts.
- [OpenChain ISO/IEC 5230 license compliance](https://openchainproject.org/license-compliance) describes the key process requirements for a quality organizational open-source license compliance program.
- [ISO/IEC 5230:2020](https://www.iso.org/standard/81039.html) identifies the international-standard scope as requirements for an organizational license compliance program; ISO lists the 2020 edition as confirmed in 2026.

## Decision Boundaries

- A license name is only the start of review. Exact text, version choice, exceptions, file scope, notices, provenance, modifications, combination, delivery, and jurisdiction can change the result.
- SPDX standardizes identification and expressions; it does not decide compatibility, ownership, enforceability, or whether a particular use satisfies obligations.
- REUSE improves traceability but does not grant rights, resolve conflicting claims, inventory dependencies automatically, or replace legal review.
- OpenChain ISO/IEC 5230 concerns the quality of an organizational compliance program. A package itself is not made compliant or safe merely because a supplier uses such a program.
- Permissive, weak reciprocal, strong reciprocal, network reciprocal, source-available, documentation, font, content, data, and model terms have different triggers. Do not generalize from software-code licenses to every asset.
- Security provenance, malware, tracking, install behavior, maintenance, export controls, privacy, and patent or trademark rights remain separate review dimensions.
