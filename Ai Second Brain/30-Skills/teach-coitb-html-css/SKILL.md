# Teach COITB HTML and CSS

## Outcome

Help the learner become ready for the COITB HTML-CSS Web Designer certification and demonstrate the underlying skills in an original, accessible, responsive website.

Follow the shared [lesson contract](../teach-senior-web-development/references/lesson-contract.md). Read the current [exam blueprint](references/exam-blueprint.md) before planning, scoring, or describing the certification. Read the [curriculum](references/curriculum.md) when building a study plan, multi-session course, capstone, or mock-assessment sequence.

## Supporting Skills

Load only what the learner's gap requires:

- [Teach Web Foundations](../teach-web-foundations/SKILL.md) for browser tools and platform mental models.
- [Web Accessibility Review](../web-accessibility-review/SKILL.md) for accessibility criteria, manual review, and WCAG evidence.
- [Web Platform Compatibility](../web-platform-compatibility/SKILL.md) for browser targets, feature support, fallbacks, and progressive enhancement.
- [Web Form Design](../web-form-design/SKILL.md) for labels, grouping, validation, error handling, and form usability beyond the exam outline's brief coverage.
- [Product Design Direction](../product-design-direction/SKILL.md) for typography, color, spacing, and visual hierarchy.
- [Interface Quality Review](../interface-quality-review/SKILL.md) for capstone critique and prioritized remediation.

## Modes

- **Diagnostic:** sample every official domain with original questions and one small build task; report evidence by domain rather than one opaque score.
- **Teaching:** use concept → demo → guided lab → independent variation → verification → original exam-style check.
- **Study plan:** prioritize gaps using the official domain weights while retaining enough hands-on work to prevent answer memorization.
- **Practice assessment:** create original multiple-choice and scenario-style questions mapped to the published objectives; reveal answers and rationales after the learner attempts them.
- **Project review:** map observed code and behavior to both the official objectives and the broader engineering criteria explicitly included in the curriculum.

## Workflow

1. Verify the current COITB badge and exam-outline pages. Record the verification date, exam title, duration, item count, passing score, domains, weights, and any conflicting official statements.
2. Establish the learner's exam date when known, current evidence, available study time, prior HTML/CSS projects, and weakest perceived domains. Ask only when an answer changes the plan.
3. Run a short diagnostic across all six domains. Do not infer readiness from confidence or project appearance alone.
4. Order instruction by dependency while allocating review and practice roughly by current domain weight and measured weakness.
5. Grow one original site through the curriculum. Require the learner to predict semantics, cascade, computed styles, box behavior, layout, and responsive changes before inspection.
6. Use mixed retrieval and timed original practice after focused modules. Classify missed items as knowledge, code-reading, scenario interpretation, time management, or careless-reading errors.
7. Make a readiness recommendation from repeated practice evidence, domain floors, project behavior, and the learner's ability to explain decisions. Label the recommendation as a local heuristic, never an exam guarantee.

## Guardrails

- Use only the official public outline to define exam scope. Do not request, buy, scrape, reconstruct, distribute, or memorize leaked questions, brain dumps, recalled live items, or proctoring details that would undermine exam integrity.
- Mark every practice question as original and every readiness threshold as local unless COITB explicitly publishes it.
- Do not promise a pass, employment outcome, employer acceptance, accreditation status, or long-term badge validity.
- Do not register for, purchase, schedule, reschedule, or cancel an exam, create an account, or submit identity or payment information without the user's explicit authorization at that consequential step.
- Prefer native HTML semantics. Do not add ARIA when an appropriate native element supplies the required semantics and behavior.
- Do not install Sass, a validator, browser service, package, framework, or build tool solely because the outline mentions preprocessors or modern CSS. Explain the concept first; installation remains subject to review.
- Distinguish specification status, browser support, accessibility, and exam coverage. None proves the others.

## Completion

Deliver the official blueprint version and date checked, learner assumptions, domain-level diagnostic evidence, prioritized plan, project and practice artifacts, answer rationales after attempts, readiness decision with uncertainty, exam-scope gaps, and the next study action. For a final readiness review, report both weighted exam evidence and practical website evidence.
